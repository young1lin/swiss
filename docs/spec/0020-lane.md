# §lane — The lane

Chapter 0020 of the [swiss specification](../SPEC.md).

One machine-wide queue for heavy commands, and the one call that tells an agent what this
machine offers. Several agents share one desktop: two `cargo build`s, or a build beside a
vitest run, starve each other until tests fail at their own deadlines and rustc runs the paging
file dry. A command run through `swiss lane run` holds a slot for as long as it runs, and
whoever comes next waits its turn.

The lane never runs anything. The CLI spawns the command in its caller's terminal; the gateway
only counts. So every refusal is open: a gateway that is down, an older gateway without the
lane, or a disabled plugin means the command runs at once, after one warning line. The lane is
a courtesy between agents, never a gate.

**The plugin** — id `lane`, label Lane, version 0.1, config schema version 1,
`restart_on_config_change: false` (a restart would close every lease, §lane.config),
`requires: []`. One page, `lane` (order 56, beside Process, layout `page`), and one route
prefix, `/api/lane`, in the extra tree (§host.routes), mounted the way the terminal plugin
mounts its routes: a slot the instance fills on start and empties on stop. While the plugin is
not active every route answers the structured 503 that names it.

## §lane.queue — Who holds a slot, who waits

- **Entries.** An entry is a ticket — `cmd`, `cwd`, `by` (the caller's agent, else `cli`),
  `session` and `pid`, every field display only and clipped, never refused (400 characters for
  `cmd`, 1024 for `cwd`, 64 for `by`, 128 for `session`) — plus an id the lane assigns,
  counting up from 1 for the life of the instance.
- **Admission.** First come, first served in arrival order. Whenever the lane changes, the
  oldest waiters take the free slots, up to `capacity`. Nothing is admitted after the lane
  closes.
- **Resume.** An entry that says `resume` was already running when the gateway restarted; it
  is admitted at once whatever the capacity, because its command runs either way, and is marked
  `resumed`. The running list may then exceed the capacity until those commands finish.
- **Leaving.** An entry leaves in one of three ways, and the most recent 30 that had started
  are kept, newest first, with `endedAt` and an `outcome`: `exit` with the reported code
  (absent when a signal took the command), `gone` when the caller's connection ended without a
  report, or `released` when the page let it go. A waiter that leaves before its turn is not
  recorded.
- **Changes.** Every change bumps a revision, wakes every holder (a watch on the revision; each
  holder re-reads its own seat) and publishes LANE.QUEUE (§bus.registry) under the lock, so the
  notices leave in commit order.
- **Closing.** When the plugin stops, or the gateway starts stopping, every holder hears
  `closed` and the queue empties. The gateway drains its connections before plugins stop
  (§host.lifecycle), and a lease never ends on its own, so the instance closes the lane on the
  bus's stop signal rather than at its own stop; otherwise every open lease would hold the
  drain to its timeout.

## §lane.config — The row

```json
{ "capacity": 1, "env": { "CARGO_BUILD_JOBS": "2", "VITEST_MAX_WORKERS": "4" } }
```

- `capacity` — how many commands run at once, 1 to 16; 1 by default, which is the point.
- `env` — the caps: variables a command gets when its caller's environment does not set them.
  Absent, the defaults: `CARGO_BUILD_JOBS=2` (rustc jobs are bound by memory, not cores) and
  `VITEST_MAX_WORKERS` at half the cores, at least 2, at most 4. `{}` means no caps. At most 32
  names, each letters, digits and `_` and not starting with a digit, up to 64 characters, each
  value up to 256.
- A new row applies in place: the queue and every holder stay; a raised capacity admits waiters
  at once, a lowered one lets the running finish. Caps reach a command when it is admitted.
- Any other key is refused, except the host's `enabled`.

## §lane.api — Routes

All behind the CLI key and the loopback boundary (§host.boundary).

- **`GET /api/lane`** → `{capacity, env, revision, running, waiting, recent}`. An entry is
  `{id, cmd, cwd, by, session?, pid?, enteredAt, startedAt?, resumed?}`; a recent row adds
  `endedAt`, `outcome` and `exit?`. `running` and `waiting` are in arrival order.
- **`POST /api/lane/enter`** `{cmd, cwd?, by?, session?, pid?, resume?}` → 200
  `application/x-ndjson`, held open: **the response is the lease**. Each line is the entry's
  seat, written when it changes:
  `{"id","state":"waiting","ahead","running"}` (`ahead` counts the entries before it,
  `running` describes the holders), `{"id","state":"running","env"}` (the caps), and as the last
  line `{"id","state":"released"}` or `{"id","state":"closed"}`. A quiet lease writes a bare
  newline every 5 s: a write to a closed socket is how the gateway learns the caller is gone,
  so this bounds how long a dead waiter holds up the queue. When the response ends for any
  reason the entry leaves (`gone` if it had started). A missing `cmd` is 400.
- **`POST /api/lane/{id}/done`** `{exit: int|null}` → `{ok: true}`: the command ended; recorded
  as `exit`. An `exit` that is not an integer or null is 400.
- **`POST /api/lane/{id}/release`** → `{ok: true}`: the lane stops counting the command, whose
  lease hears `released`. The command itself runs on.
- An id the lane does not hold is 404 with code `lane.unknown`.

## §lane.cli — `swiss lane`

```text
swiss lane [status] [--json]                 who holds the lane, who waits, what finished
swiss lane run [--wait DUR] [--] <program> [args...]
swiss lane release <id>                      stop counting a stuck holder; it runs on
```

`run` takes its own flags first; `--`, or the first word that is not one, starts the command.
It resolves the program on `PATH` (with `PATHEXT` on Windows; not found is exit 127), opens a
lease, and waits, printing a line on stderr only when the queue moved. When its turn comes it
spawns the command **as its caller would have**: the same directory, the caller's original
environment (the variables the CLI strikes from itself at startup are handed back,
§host.cli), and the lane's caps added only where the caller set nothing. stdin is inherited;
stdout and stderr go to this terminal and to a log under `~/.swiss/lane/` (the newest 50 are
kept). On Windows the command runs in a kill-on-close job, so a killed CLI takes it along and
the lane never counts a command nobody waits for. It exits with the command's code (128 +
signal on unix), after a last line on stderr that names the exit, the time taken and waited,
and the log.

- `--wait DUR` gives up after DUR: exit 75, nothing run. Ctrl-C while waiting is exit 130,
  nothing run; while running, the first Ctrl-C reaches the command, a second kills it.
- A refused lease (503: the plugin is off; 404: a gateway without the lane; no gateway) runs the
  command at once after one warning line.
- **Restarts.** A lease that closes or drops while waiting is opened again, queueing anew; one
  that closes while the command runs is opened again with `resume` (§lane.queue). Either
  retries every 2 s for a minute; a lane that does not come back lets the command run, or keep
  running, outside it. A lease silent for 20 s counts as dropped.
- A command that replaces the swiss binary (a deploy or update script) is not run through the
  lane: the CLI holds the binary open for the command's whole run.

## §lane.panel — The Lane page

One page, `#lane`: the capacity and the caps, then the running commands (id, who, since when,
command, directory), the waiting ones in order, and the recent ones with their outcome and
duration. A running or waiting row has a Release button (`POST /api/lane/{id}/release`). The
page reads `GET /api/lane` on mount and again on each LANE.QUEUE notice, coalesced
(§bus.topics); it has no timer. The ages it shows are computed at render time from the
timestamps. Release answers a 404 `lane.unknown` with the localized "already gone" note.

## §lane.brief — `swiss brief` and the `swiss-brief` skill

`swiss brief [--json]` is the one call that tells an agent what this machine offers. It reads
`/health` first; a gateway that is down gets one line saying so and `swiss start`. Otherwise it
reads the lane, the MCP servers, the remote targets and endpoints, the managed apps and the
tunnels at once, each with a 3-second timeout, and prints a section for each with the command
that uses it: `swiss lane run`, `swiss connect`, `swiss remote brief`/`exec`, `swiss process`.
Only enabled tunnels are listed, and a section lists 20 rows at most, then counts the rest. A
plugin that is off or a route this build lacks prints as such. The memory section is read
offline from the store (never created) and names this directory's project, or suggests
`swiss memory init`. `--json` is one object with the same facts. It always exits 0: a briefing,
not a gate.

The `swiss-brief` skill (`src/skill_assets/brief/SKILL.md`) loads by itself before a build or
a test suite, and teaches the lane, `swiss process` and the rest of the brief. Its Claude Code
copy runs `swiss brief` as it loads, the way `swiss-remote` runs its brief (§host.cli).
