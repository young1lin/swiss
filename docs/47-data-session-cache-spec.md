# 47 — Data：按连接停放会话，回来即现，后台增量校验

> 状态：**已实施**（分支 `data-cache`，2026-09-25）。起因是主人的原话："我点了 MYSQL，再点 Redis，再点回去，
> MYSQL 的所有内容都没了……Data 切换的时候要有缓存，增量更新，不然每次都是刷新"。

## 0. 现状（改之前）

- `dbSwitchConn`（data-view.ts）切连接时把连接记录逐字段清零（表目录、树的展开、排序、搜索、database 目录、
  Redis 的 key 遍历），再 `dbResetTabsForConn()` 把整条对象 tab 换成一个空占位符。有暂存写入就先弹确认，
  因为切走等于丢弃。
- 页面卸载（去别的插件再回来、文/A 切语言）走 `unmountDbView()`：两份记录都回到初始字面量，回来时
  `loadDbView` 发现 `conn` 为空，就选第一个连接（所以 P9 走查时看到"回到 demo-cache"）。
- 结果：每次回到一个连接都从零开始——重新拉表目录、打开的表全关、页码/过滤/排序全丢、Redis 已经 More
  进来的 key 页也丢。

## 1. 决定

| # | 决定 | 为什么 |
| --- | --- | --- |
| D1 | **会话 = 连接记录 + tab 条 + 当前下标**，按连接名停放在 db-state.ts 的一个 Map 里。切连接是"停放当前、取回目标"：对象整体换，不逐字段拷贝。 | 整体换对象让在途请求天然落回它所属的会话（它们在 await 前捕获了记录/ tab），不会写进正在看的连接。 |
| D2 | 切连接**不再确认**：暂存写入跟着会话停放，没有东西被丢。 | 确认框的存在理由是"切走会丢"；不丢了，再问就是噪音。 |
| D3 | 页面卸载也停放会话，并记住最后一个连接；下次挂载先恢复它。离页确认（`canLeave`）照旧问暂存写入，用户确认后**丢弃所有会话的暂存写入**，其余（目录、tab、行页）保留。 | 离开 Data 页以后，浏览器的 beforeunload 只问前台页面，停放的写入就没有任何守卫在数了；只保留有守卫的东西。 |
| D4 | `hasPendingChanges()` / `canLeave()` 数**所有会话**的暂存写入（当前 + 停放）。 | 在 Data 页里关浏览器标签时，停放在 MySQL 会话里的编辑也必须被问到。 |
| D5 | 恢复后先用缓存立刻画出来，再**安静地增量校验**：表目录与前台表的当前页按原坐标重拉，没有 Loading 提示、不清空；回来的内容与手上的一致就什么都不重画（滚动、选中、焦点都不动），不一致才替换重画。前台 key 的值同理（有暂存编辑时不碰）。 | 这就是主人说的"增量更新"：看到的是缓存，校验在后台，只有变了才动。 |
| D6 | Redis 的 key 列表恢复后**不重扫**；SQL 控制台结果**不重跑**。 | SCAN 是游标分页，重扫会丢掉 More 进来的页；重跑查询可能有副作用。它们都有自己的显式刷新。 |
| D7 | 停放上限 8 个会话，超出按最久未用淘汰；**带暂存写入的会话永不淘汰**。`/api/db` 里已经不存在的连接，其会话随之丢弃。 | 连接数通常个位数；上限只防病态情况。丢编辑永远不是对的交换（同 docs/42 D3）。 |
| D8 | 停放时停掉 Activity 的 5s 轮询、把各 tab 的 `loading`/`detailBusy` 复位；恢复时经 `dbAfterTabSwitch` 重启轮询、补拉缺的数据。 | 被切断的加载不能在恢复后留一个永远转的 spinner；后台会话不该继续问服务器。 |
| D9 | `unmountDbView()` 保持"全部清空"（含停放区），它是测试的重置口；页面卸载改用新的 `dbSuspendView()`。 | 二十多个测试文件用它做用例间隔离。 |

## 2. 不做什么

- 切 **database**（同一连接内，docs/43 M3）仍然是原来的整条重置 + 确认：它换的是同一连接的目录轴，
  按 (连接, 库) 停放是另一层键，等主人要再做。
- 不做跨浏览器刷新的持久化（localStorage/IndexedDB）：行数据可能很大，且是服务器上的真相，刷新页面就该重读。
- 连接抽屉里不给"有停放编辑"的连接加标记（离页/关页的确认会把总数说出来）。
