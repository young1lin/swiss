# Tunnels Plugin: SSH Tunnels and Port Forwards (swiss-tunnels)

> Tunnels is the panel's SSH tunnel manager: it maintains a set of SSH server connections and the local port-forward rules attached to them (each rule forwards `127.0.0.1:localPort` over SSH to a remote `targetHost:targetPort`), keeps `enabled` rules up permanently, auto-reconnects on disconnect with exponential backoff, stores credentials only as `${ENV_VAR}` references, and provides MCP with read-only matching of "which rule serves which MCP" plus rename/delete guards.

The module header comment states plainly: the Node build's `authed` wrapper has no per-route counterpart in this build — **the route boundary is the gate** (api.rs:3-6). The plugin descriptor declares `routes: vec!["/api/tunnels"]` (src/builtin.rs:270).

## Configuration and Storage

- **tunnels.json** (sealed envelope, `write_secure_json`/`read_secure_json`, same format as every state file): structure `{connections:[…], rules:[…], ruleGroups:[name], connGroups:[name]}` (store.rs:237-245). Connection key order id/name/host/port/username/authType/(keyPath/passphrase/password/hostKey/group optional, absent-not-null) (types.rs:128-152); rule key order id/name/connectionId/localPort/targetHost/targetPort/remark/autoReconnect/reconnectInterval/enabled/mcps/(group optional) (types.rs:178-198; the key order is the file format — serialization is a hand-written Map preserving Node field order, types.rs:1-6).
- **Credentials stored as references only**: password/passphrase may be `${ENV_VAR}`; the reference is what lands on disk, resolved at connection time in ssh.rs (strict: a missing variable errors, docs/19 D4); API outbound masked via `mask_conn`, inbound round-trips through `unmask_conn` with the MCP panel's sentinel (api.rs:54-69) — the browser never receives plaintext, and editing unrelated fields cannot destroy stored secrets.
- **Load fault tolerance**: corrupted file → warn + empty tables (store.rs:113-119); row-level discard rules: connections/rules with an empty name/host or an invalid localPort are discarded, but **rules with an unknown connectionId are kept** (presented as error rather than vanishing — one bad hand-edit does not eat the other 17 rows, store.rs:174-176); group lists filter out empty strings and default at read time.
- **Validation constants**: localPort/targetPort must be integers in 1..=65535; **the gateway's own port is refused as localPort** (store constructor parameter `gateway_port`, store.rs:90-91); reconnectInterval goes through `interval_or` (NaN/0→10, floor of 1, store.rs:66-71); name uniqueness, ports not colliding with other rules, etc. live in valid_conn/valid_rule.
- **groups**: since docs/20 G3, `default` is an ordinary name listed explicitly (the `tunnelGroupsV2: true` marker makes the list literal — a pre-groups file gets `default` materialized at the front); rename migrates members and counts them; deleting a group drops its members into the FIRST group; every mutation runs through the host's `Groups` rules (crates/swiss-host/src/groups.rs) — the tunnel store keeps only its two key names.
- **host_key**: `SHA256:…` fingerprint, learned on first connect (`set_host_key`); `update_connection` **re-adopts** the old key when host/port are unchanged (preventing an edit from silently dropping trust), hence the dedicated `clear_host_key` (trust reset) and `trust_host_key` (manager.rs:1135-1173; store.rs:529-552).
- **No separate config row**: the plugin's `config_schema` is an empty object (builtin.rs:268); all state lives in tunnels.json; the credential-reference rules match the global `${ENV_VAR}` contract.

## Lifecycle and Background Behavior

- **Enabled/running/visible as three states**: descriptor id=tunnels, kind="tunnels", page order 30, routes [`/api/tunnels`] (builtin.rs:261-274); `restart_on_config_change: true` (this plugin has no config row, so the flag has no practical effect). Disabling goes through `POST /api/plugins/tunnels/disable`: the route tree answers host 503, the nav group disappears (inventory-driven).
- **start** (builtin.rs:301-341): (1) after the store loads, if `is_fresh()` (no file), run the forward-port import first — **the import lives inside start**, so a disabled plugin no longer touches tunnels.json at boot; (2) `manager.reopen()` synchronously lowers the close_all gate first (a Start click racing ahead of the boot task is not rejected as closed); (3) `scope.spawn` starts `start_enabled()` (starts only enabled rules; each failure only warns, isolated) — **a task supervised by PluginScope**, accounted for and cancelled when the host stops; (4) register the shell capability **last** (a failed start leaves no provider behind, docs/12 W3/docs/14 §4).
- **stop** (builtin.rs:343-358; docs/12 W3 order): `services.shells.begin_withdraw` (no new terminals admitted) → `shells.ledger().begin_withdraw` + `drain_sessions` (short drain window; on timeout, names how many were closed) → `manager.close_all()` (each rule closes its Forward to release the port; SSH client `end()` has a 1.5s cap; **the enabled flags are untouched**, the next start restores the original set, manager.rs:1386-1388) → `services.shells.clear()`.
- **Per-rule operation serialization**: one runtime per rule (`rt(id)`), holding a per-rule tokio mutex across the whole operation (the counterpart of Node's promise `enqueue`); mutable run state is snapshotted out after a short std lock — **never hold a lock across an await** (manager.rs:12-15).
- **One client per connection, reference counted**: `acquire`/`release`/`put_ref`; 14 rules on the same host dial only once, and end happens only when the last user leaves (manager.rs:9-10, 453-483); PTY sessions likewise take a reference via `put_ref` (`open_shell`, manager.rs:504-535).
- **Background task inventory**: no tick — tunnels has no periodic task; what exists is event-driven: the SSH transport watcher (one per client, polls is_closed every 100ms, ssh.rs:363-372), disconnect-recovery ops (`on_connection_lost` spawn), reconnect timers (`schedule_retry` spawn, weak-reference upgrade, abortable by clear_retry), and each forward's accept loop and pipe tasks (forward.rs). All are reclaimable by close_all/stop.
- **Process shutdown order** (server.rs:341-359): the host stops in reverse registration order — jobs→data→**tunnels (releases all local ports before the MCP registry, while MCP connections are still draining)**→MCP; afterwards `services.shutdown()` reaps ownerless runs.
- **Boot order** (builtin.rs:63-65): registration order MCP→Tunnels→Data→Jobs→Process, started in reverse — **tunnels comes up before any MCP that may ride on it** (the same convention as Node, mod.rs:28-32).

## Relationship to the Host and Other Plugins

- **Plugin descriptor registration**: one `TunnelsPlugin` factory + a single `host.register` line (builtin.rs:72-76), zero host changes — the docs/09 §9 "add a plugin without touching the host" path. The wrapper comments follow the docs/09 §4 honesty rule, stating what disable truly does and does not do.
- **Toward MCP: optional association, no dependency cycle** (docs/09 §3 "Tunnels boundary", docs/09:86-90): the tunnels side defines only two narrow traits — `McpView` (has/stateOf/isStarted/startedAt, manager.rs:167) for the stop guard and in-row MCP state, `McpDisplay` (names/suggest, api.rs:34-39) for suggest and in-row names; the registry-backed implementations live in the **composition layer** `src/mcp_link.rs`, so swiss-tunnels does not depend on swiss-mcp's types (ADR-010 boundary preserved). docs/09:90's "SSH-dependent connections need the tunnel available before connecting" is carried by boot order (tunnels up first) plus MCP-side reconnecting; "forward rules used standalone stay up permanently and must not be reaped merely because an MCP has no traffic" manifests as rule lifecycles fully independent of MCP traffic.
- **Toward Terminal (shell capability)**: `TunnelShells` implements `ShellProvider` and registers into `services.shells` (shell.rs); the terminal plugin never links an SSH client (docs/14 T2); targets are exactly the tunnels connections — no second host list, no credential copy, no host-key decisions.
- **Toward host RuntimeServices**: consumes only the `services::shell` registration slot; provides no action and never enters the RunCoordinator.
- **With Data/Jobs/Process**: no direct relationship whatsoever (subsystem crates do not depend on each other; invisible at the Cargo.toml level).
- **Routes and boundary**: the `/api/tunnels` tree is merged by the composition root inside `build_app`'s loopback guard and plugin boundary (server.rs:254-268); loopback is a security boundary, not a default (AGENTS.md load-bearing rule).

## Style and Design Observations

**Project-wide patterns followed**:

1. **Plugin descriptor registration**: one factory + one register line; the descriptor carries kind/label/pages/routes/requires, and the host clears out navigation and the 503 boundary (module self-description at builtin.rs:1-8). The wrapper comments enforce docs/09 §4's "honesty rule" — item by item, what disable does/does not do (builtin.rs:286-290).
2. **Route mounting**: state-resolved `Router<()>` merged by the composition root, inside the same loopback guard + body cap + plugin boundary; no per-route auth — the boundary is the gate (explicitly stated at api.rs:3-6).

**Inconsistencies/exceptions**:

- **Deliberate retention of JS Number() semantics**: store/api accept NaN-defaults, numeric strings, boolean coercion (types.rs:14-61), and error text renders the coerced value — this looseness is **retained** for byte-level compatibility with the Node build's tunnels.json/API, the opposite of jobs def.rs's strict new world where "strings/fractions/negatives are always type errors"; both sides' comments state the reason (tunnels is a port, jobs is Rust-native).
- There is one `.expect()` in `new_id()` (types.rs:70-72) — an OS CSPRNG failure is treated as a broken machine, and the comment explicitly declares the exception; this is a declared exemption from the repo-wide "no unwrap on config/network/disk" discipline.
- The panel's `state.tun.keys` is cached forever (never invalidated after first load), unlike the other data polled every 6s — a deliberate trade-off for a low-frequency static directory.
- stop-all's 409 blocking list reuses the Dependents structure for "the MCPs that depend on this"; semantically these are not "delete users" but "stop users" — a broad use of the same funnel.
- The tunnels page has no boot probe like jobs.js's (404/503 hides the tab): Tunnels has existed since the Node era, and the tab's visibility is left entirely to the /api/plugins inventory (docs/09 §6's "the frontend must not decide the capability tree from probe-endpoint success" is a transitional exception in jobs).
