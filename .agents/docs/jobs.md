# Jobs Plugin: Config-Driven Scheduled Tasks (swiss-jobs)

> Jobs is a config-driven scheduler: job definitions (v2 schema) exist only in the `plugins.jobs.config` config row; the scheduler is one producer of the shared RunCoordinator (executing any registered Action, by default `process.legacy-command`/`process.exec` subprocesses); a once-per-second map scan decides triggering; occurrence anchors/misfire/DST/retry semantics persist in jobs-state.json; every run is recorded line by line into `logs/jobs/<id>.jsonl` — the contracts of docs/10/11 are fully implemented.

## HTTP API and Routes

**The plugin's own endpoints** (`mount(jobs: Arc<JobSystem>) -> Router`, api.rs:137-250; merged by the composition root inside the loopback guard and plugin boundary, server.rs:261-268; descriptor routes=[`/api/jobs`], builtin.rs:545). All 5 enumerated:

| Method+Path | Request | Success response | Failure |
| --- | --- | --- | --- |
| GET `/api/jobs` | — | `{jobs:[job_view…]}` | Plugin disabled 503 (host boundary) |
| PUT `/api/jobs/{name}` | body: `{command, everySec?\|cron?, enabled?, timeoutMs?, cwd?, env?}` (v1 shape; the URL is the identity — the path's name wins) | `{job}` (incl. live facts) | 400 Invalid; 409 NotEditableV1 (`use PUT /api/plugins/jobs/config`); 500 Persist (write_status, api.rs:50-59) |
| DELETE `/api/jobs/{name}` | — | `{deleted:name}` | 404 unknown job; write failure 500 (removed from the table but the config row not persisted = it comes back at next boot, so no success is reported) |
| POST `/api/jobs/{name}/run` | Default empty body; or `{"async":true}` | Synchronous: 200 `{run:record}`; async: 202 `{runId:N}` | 404 Unknown; 409 Busy (label already running); 429 Capacity; 503 Unavailable (capability not registered) (fail, api.rs:61-72) |
| GET `/api/jobs/{name}/runs` | q: `limit` (default 20, clamped 1..100), `cursor` (the docs/11 §7.3 spelling)/`before` (alias for the old spelling) | `{runs:[…newest first], nextBefore?:<seq>}` (nextBefore absent when exhausted) | Illegal name 404 (api.rs:223-225) |

**job_view row shape** (mod.rs:991-1031): v1 fields (name/command/everySec\|cron/enabled/timeoutMs/cwd/env, `to_v1_view` def.rs:991) + v2 fields (title/labels/trigger/action/overlap/misfire/retry/output, `v2_view_fields` def.rs:1113) + `source:"config"`, `actionAvailable`, `configRevision` (the config revision in force, guarding against stale lists), `lastRunAt`/`lastOk` (from the state file), `running` (coordinator label count; manual submissions count too), `nextDueAt` (absent when disabled).

**Host/shared endpoints Jobs depends on** (not this plugin's routes, but they complete its surface):

| Endpoint | Owner | Role in Jobs |
| --- | --- | --- |
| GET `/api/actions` | Host (services/api.rs:45) | Source of the advanced form's action dropdown and input schema (run.js's argFieldsHtml) |
| POST `/api/runs` | Host (services/api.rs:46, 94-147) | The manual submit gate (owner="manual", a producer on equal footing with jobs); 202+runId returns immediately |
| GET `/api/runs/{id}` (`?output=0`) | Host (services/api.rs:155-168) | Run now polls for a terminal state; the run view is flat (`{runId,state,ms,…}`) |
| POST `/api/runs/{id}/cancel` | Host (services/api.rs:172-183) | Cancels and **waits** (returns only after the subtree is reaped and the read ends joined) |
| GET/PUT `/api/plugins/jobs/config` | Host (host/api.rs:52) | The only CRUD surface for v2 definitions (no second endpoint set, docs/11 §7.2); PUT passes through `validate_jobs_config` (builtin.rs:433-440) |
| POST `/api/plugins/jobs/enable\|disable` | Host (host/api.rs:50-51) | Lifecycle switches |
| GET `/api/plugins` | Host | Page inventory/navigation/dependency decisions (docs/13) |

**Error contract**: `admin_error`/`admin_json`, camelCase, absent-not-null; camelCase status-code semantics follow the same convention as the tunnel API (api.rs:1-5); `whole_number` tolerates a JS client's 60.0 spelling but rejects fractions/NaN (api.rs:36-48).

## Panel Pages and Interactions

Panel assets are edited directly in this repo (ADR-016). The Jobs page entry `js/views/jobs.js`: `mount` (inventory missing and probe failing → the "Jobs unavailable" placeholder)/`refresh`/`poll` (`loadJobs(true)` patch)/`countText` (`jobsChipText`)/`unmount`.

- **Availability probe** (jobs.js:28-41): a bare `GET /api/jobs` at boot — both 404 (old gateway) and 503 (subsystem disabled) hide the jobs button in `#viewSeg`; network errors are assumed to mean present. This is a transitional exception (docs/09 §6 says the frontend must not decide the capability tree from probe endpoints; views/jobs.js:15 prefers `pluginInventory()`).
- **List rendering** (jobs.js:45-66; polling.js:148-177): `.wide` + the same `tun-row`/`tun-foot` frame as Tunnels; row = dot + title (±id ±#labels ±off) + command code + triggerSummary + data-last/data-next; a full redraw happens only when the structural signature (`name\n…`) changes, and `patchJobs` only touches dot/title, last/next, the Run now button and the footer (jobs.js:68-95). Dot: running→starting, !enabled→idle, lastOk=false→down, ran and succeeded→up, never ran→idle (polling.js:139-146).
- **Run now** (jobs.js:133-165): submits `{"async":true}` to get a runId, then polls `GET /api/runs/{id}` at 1s intervals to a terminal state (**capped at 1800 tries = 30 minutes**; on timeout it points you to History); reads the flat run view; toasts the result at the end and `loadJobs`.
- **Row overflow menu** (docs/18 V5): Edit (`editableInV1===false` goes straight to the advanced form)/History/Delete (the confirmation text states plainly that history is kept on disk).
- **v1 create/edit form** (jobs.js:177-468): schedule builder with four presets (interval/daily/weekly/monthly) + raw cron as a fifth mode; **cronstrue (vendored locally, MIT) reads the expression into an English sentence, and the sentence is the validation** (jobs.js:179-197); the command textarea folds newlines into spaces and previews the joined result (one job, one process); timeout entered in minutes; the env box takes KEY=VALUE per line, and a bad line blocks saving (jobs-v2.js:149-166).
- **Advanced (v2) form** (jobs.js:470-…; jobs-v2.js): `GET /api/plugins/jobs/config` reads the row → replaces this definition → PUTs the whole row with the just-read revision (no second CRUD surface); the action dropdown comes from `GET /api/actions`, and the input form is generated from that capability's own schema (run.js argFieldsHtml); unregistered types prompt a switch to the JSON editor; the form writes only the keys it owns, and **unknown-but-legal fields round-trip with the object and are not lost**; the JSON editor and the form are two views of one object (`v2ToForm`/`formToV2`/`defTemplate`).
- **History table** (run-history.js + jobs.js openRunsSheet): cursor pagination (`cursor`/`before`), nextBefore drives "earlier".
- **chip**: the footer and navigation counts share one builder `jobsChipText` (`N jobs · M on · K failing`, polling.js:179-185).

## Configuration and Storage

- **The single source of definitions = the `plugins.jobs.config` row in `gateway.config.json`** (sealed; managed by ConfigStore with a revision; in force since S3). Row structure (def.rs:29-83, 560-591; schema-lite metadata builtin.rs:455-543): `schemaVersion` (2 only)/`maxConcurrentRuns` (1-64, default 2)/`maxQueuedRuns` (0-1024, default 32)/`retention{days 1-3650 default 180, maxBytesPerJob 65536-67108864 default 2097152, maxHistoryBytes 1048576-1073741824 default 67108864 — accepted and stored by this build, but cross-file accounting is S5 remainder work}/`definitions` (≤512 entries, MAX_DEFINITIONS def.rs:34-36; keyed by id = the run-log file name).
- **Definition field contract**: title (≤200 chars, defaults to id)/labels (≤16 entries, each ≤64)/disabled (default false = enabled by default)/trigger (manual\|interval{everyMs 1000..31_536_000_000, firstRun after-interval\|immediate}\|cron{expression 5 fields, timezone local only})/action{type, input (${ENV_VAR} references preserved verbatim, schemaVersion)}/timeoutMs (1000-86_400_000, default 600_000=10min)/overlap (skip\|queue-one)/misfire (skip\|run-once)/retry{maxAttempts 1-10 default 1, delayMs 0-3_600_000 default 0, backoff fixed\|exponential, retryOn[failure,timeout] default [failure]} with a total bound ≤24h/output{capture tail\|none, maxBytes 1024-1_048_576 default 16384}. **Numbers must be whole and non-negative**: strings/fractions/negatives are type errors, not silently defaulted (def.rs:19-21, 234-247); the tolerated 60.0 spelling is the exception.
- **jobs-state.json** (sealed, same directory as jobs.json; state.rs:5-23): one line of **facts** per job — `lastOccurrenceKey`/`lastRunAt`/`lastOk`/`lastRunId`/`consecutiveFailures`; a missing file = empty state, not an error; corruption = empty state + warn, boot not blocked; a write failure = warn, not an error (the run already happened); unknown keys/bad types degrade field by field to absent. Definitions (intent) and facts live in separate files — editing a definition can neither forge nor lose "last run" (docs/10 §5).
- **logs/jobs/<id>.jsonl**: one line per attempt; seq assigned first-field by append_run (restored from the last line after restart); over max_bytes in size → trimmed to keep (=maxBytesPerJob/2); over retention.days in age → cleaned by the hourly sweep (runlog.rs:33-70; server.rs:289-304); private permissions on directory/files; RunLog is an **instance** held by JobSystem, not a process-wide global (S2, runlog.rs:14-18).
- **jobs.json (v1)**: read-only after the S4 migration — `migratedAt` marker + jobs array emptied + `jobs.json.v1.bak` sealed backup (migrate.rs:1-18); no double-writing (docs/11 §10).
- **Credential discipline**: ${ENV_VAR} references inside action.input (and v1 command/cwd/env) are persisted **as references**; resolved at runtime inside the capability — `process.exec` strict (a missing variable is a named error), `process.legacy-command` lenient (old semantics: unset variable = empty string) (actions.rs:5-12); resolved values (≥8 chars) register into output masking, masking only ref-resolution results, never user literals (actions.rs:62-78, 377-383); resolved values are never written back, never in error messages, never in the run index (docs/11 §2 rule 2).

## Lifecycle and Background Behavior

- **create** (builtin.rs:591-611): (1) `migrate::run` **first** — any failure makes the plugin Failed, jobs.json untouched and unmarked, and the scheduler never runs on a half-migrated tree; (2) read the store's current row (the migration may have already merged v1 definitions in); `{}` falls back to the passed-in config; (3) `apply_config` lands the table.
- **start** (builtin.rs:629-632; mod.rs:488-505): `rebuild_next_due` + a fresh cancel channel + spawn of the **single** tick task (each second: sleep→scan table→spawn occurrences). No resident task per job; a restart revives it with the same channel.
- **stop/shutdown** (builtin.rs:634-643; mod.rs:507-531): stop = abort the tick + send cancel (occurrences sitting in a retry delay abort immediately); shutdown = stop + `runs.cancel_owner("jobs")` **cancels by owner and awaits** (returns only after the subtree is reaped and the pipe read ends joined) — reaps only jobs' runs, the `manual` producer's runs are untouched (docs/10 §2). After disabling, definitions/lastOk/all history are kept; enable restarts the tick, and the next due occurrence proceeds as usual.
- **apply_config applies in place** (mod.rs:362-405; builtin.rs:649-654): `restart_on_config_change: false` (deliberate since S3 — a restart would cancel in-flight runs, in-place application is the whole point, builtin.rs:546-551); swap table → push capacity set_capacity → re-budget runlog → full next-due recompute; in-flight runs finish with the definition snapshot they claimed (docs/11 §8); on apply failure the host stays Active and exposes the desired/actual difference.
- **Boot validation, two tracks** (builtin.rs:556-589): PUT is strict (`parse_with_actions`: unknown fields/bad values 400, action.input validated against the resolved capability's schema — a saved job can never carry input that would be rejected on first run; an unregistered action is only a warning); boot is lenient (`parse_boot_with_actions`: object placeholder rows possibly left by old validators are dropped + warn, one stale entry does not eat the whole table; non-object remains fatal). One parser, two policies (`parse_at(config, boot)`).
- **The occurrence execution chain** (mod.rs:654-798): due → read the definition snapshot → `missed_occurrences` counts the missed → occurrence key idempotency check → **claim first** (the anchor moves to the occurrence instant regardless of what follows — skip/refuse/run — otherwise a full pool would re-trigger the job every tick, the §6.2 invariant) → with misfire>1 record a summary (skip stops here) → the retry loop (each attempt is an independent submit, the global capacity applies per attempt; the delay between attempts is `select!`-ed with cancel so stopping the plugin aborts immediately) → canceled/refusal never retried → `persist_last_ok` (a refusal does not land in lastOk — an exit that never happened cannot be claimed; a settle after the definition was deleted is skipped).
- **Background task inventory**: the single tick task (plugin-scoped); `server.rs`'s boot + hourly sweep task (`sweep_run_logs`, same cadence and reason as the call log — append-time checks cover only still-running jobs, server.rs:289-304); the accounting spawn for the async manual gate; the shared coordinator's run tasks (owner is where they live). Scheduling tests do not sleep (injected clock; docs/11 §11.6).
- **Shutdown order** (server.rs:341-359): reverse registration order — **jobs stops first** (the scheduler before data/tunnels/MCP), then `services.shutdown()` reaps ownerless runs.

## Relationship to the Host and Other Plugins

- **Descriptor registration**: id=jobs, kind="jobs", page (`jobs`, order 50, no sidebar), routes=[`/api/jobs`], requires=[] (builtin.rs:444-553); one factory, one register line, zero host changes.
- **Shared run service (producer/provider/jobId semantics, docs/10 §2)**: `RuntimeServices.runs` (RunCoordinator) uniformly registers every execution — `owner` (producer: `jobs`/`manual`; cancellation is scoped by owner), `label` (`job:<id>`, the overlap-decision key), `action_type`+`input` (provider capability), runId (the coordinator's monotonic id, entering records/state/API replies). The coordinator guarantees: bounded (maxConcurrent/maxQueued, driven by the Jobs config), owner-scoped cancellation, first-wins terminal states, accepting only cancelable capabilities, and cancel awaiting until the subprocess is reaped (runs.rs:1-24). The Jobs scheduler is just one of the producers — stopping Jobs does not affect manual Action execution and cannot cancel someone else's runs (docs/10 §2, the original text landed).
- **The Process plugin = capability provider**: registers the two actions `process.exec` (typed: program+args array, strict refs) and `process.legacy-command` (v1-compatible command string, lenient refs) (builtin.rs:661; actions.rs); disabling it → the capabilities vanish from `GET /api/actions`, jobs submissions are refused 503, rows show `actionAvailable:false` — the missing dependency is visible as it is (docs/09 §9); Process has no page and no routes (a pure capability plugin, docs/09 §3).
- **With Tunnels/Data/MCP**: no crate dependencies, no runtime interaction (subsystems are peers; if some job's command happens to go through a tunnel port, that is the user's command's business — the plugins are unaware of each other).
- **Host consumption surface**: the validation authority for `/api/plugins/jobs/config` is this plugin's `validate_config` (the v2 model is the server-side authority; errors carry dotted paths); the host boundary answers 503 for a disabled plugin's paths.
- **Panel contract**: the panel JS is the spec for the admin API (AGENTS.md); Run now's async+polling is exactly docs/11 §7.3's two-gate design — an HTTP request never owns a background task's lifecycle (services/api.rs:10-12).

## Style and Design Observations

**Project-wide patterns followed**:

1. **Plugin descriptor registration**: one factory, one register; the descriptor carries the page (order 50)/routes/config_schema (self-described as "schema-lite, the real authority is validate_config"); adding Jobs touched zero host lines (the docs/09 §9 contract path).
2. **Route mounting**: state-resolved Routers merged inside the same loopback guard + body cap + plugin boundary; new endpoints always live inside the existing `/api` guards (docs/11 §2 rule 7); v2 **adds no CRUD endpoints** — `/api/plugins/jobs/config` is the only definition-editing surface, and the v1 endpoints fold writes into the same row (one source of truth, docs/09 §5).
3. **Error handling**: `admin_error`/`admin_json`, camelCase, absent-not-null; typed errors (WriteError→400/409/500, RunError→404/409/429/503) rather than string guessing; config errors carry **dotted paths** pointing at the offending field; "accept but don't execute = lying" — unimplemented semantics were uniformly rejected with 400 rather than silently ignored (docs/11 §2 rule 5; the gate came down once S5 fully implemented them).
4. **Naming and wire contract**: camelCase on the wire, snake_case in Rust; the seq-first JSONL line shape is of the same family as the call log; one builder (`ran_record`) serves both file lines and API replies to prevent drift (mod.rs:1141-1145).
5. **Memory discipline**: one tick per second instead of a task per job (current_thread discipline); the next-due table pushes calendar walks to apply/claim time; new dependencies like `chrono-tz` were excluded by rule (docs/11 §10, default-weight review); no new thread pools; output captured under byte caps, history read at page cost; the acceptance clause that disabling/enabling a hundred times still reclaims resources (docs/10 §9).
6. **Credential discipline**: ${ENV_VAR} references on disk, runtime resolution inside the capability, resolved values registered for masking, never written back and never in errors — the single-point `resolve_with_secrets` scanner shared by the whole family.
7. **State semantic separation**: definitions (intent, the config row, write failures must error) vs facts (the state file, write failures only warn) vs history (the runlog, outliving the job's lifecycle) — three files, three policies, the same trade-off stated in every relevant comment (state.rs:15-20).
8. **UI presentation**: the panel is the spec (bytes untouchable); poll-safe patching (structural signatures); confirm on destructive operations; Run now's bounded 30-minute polling; reuse of the Tunnels row style (`tun-row`).
9. **Test discipline**: the vitest suite ported case by case + injected clocks (no sleeping) + real acceptance coverage for a migration interrupted between two steps (docs/11 §11); FakeClock makes DST assertions independent of the machine timezone.

**Inconsistencies/exceptions**:

- **Jobs is a Rust-native addition with no Node counterpart**: mod.rs:4-7 states plainly that this is a "documented deliberate divergence" — once the panel page was added in the right order (the Node repo builds the panel first, then it is copied over), the /api/jobs shape became the contract. This makes Jobs the repo's only plugin with "Rust API first, panel later"; hence `whole_number`/numeric strictness coexists as a second philosophy alongside tunnels' JS `Number()` replication (each with its own comment declaring it).
- `jobs.js`'s boot probe (404/503 hides the tab) is a historical transition: when an old gateway lacks /api/jobs the page hides itself — contrary to docs/09 §6 "the frontend must not determine the capability tree from endpoint probes", mitigated by the dual track of `pluginInventory()` first + probe as fallback (views/jobs.js:14-17).
- `retention.maxHistoryBytes` is parsed, stored, and present in the schema, but the cross-file total-budget accounting is unimplemented (stated plainly in the runlog.rs:59-63 comment) — "accepted but not executed" is explicitly accounted for in comments + docs, not a silent lie.
- The panel Run now polling's 30-minute client-side cap is a bound the UI adds itself; the backend has no such constraint (the job's timeoutMs is the real bound); the comment spells out the division (jobs.js:145-147).
