# Host and Core Mechanisms (swiss-host / swiss-core / CLI)

> swiss-core provides platform primitives unrelated to "gateways" (paths, JSON-line logging, atomic writes, the sealed envelope, DPAPI/process-tree/job-object/PTY platform seams); swiss-host provides the mechanisms every subsystem shares (the plugin host and lifecycle state machine, the Action/Run services, the process supervisor, the connection catalog, the remote transport registry, the config store, the loopback security boundary, token/mask/mem/pathenv); the root src/ does composition and the CLI only — together the three form the skeleton outside the "everything" of "every capability is a plugin".

## HTTP API and Routes

**Two trees, three layers of defense** (src/app.rs:593-618): the main tree (panel/health/api/db/adminapi/MCP catch-all under `/mcp/{path}`) and the extra tree (tunnels/jobs/actions+runs/terminal/plugins management plane) each carry ① loopback_guard (peer+Host+Origin, 403 {error}, src/app.rs:218-252) ② DefaultBodyLimit (2 MiB) ③ plugin_boundary (plugin-owned prefixes only, 503 when not serving). The boundary sits inside the loopback guard — "security answers before plugin state does". 404 and wrong-method both return a uniform {error:"no route for ..."}, not axum's default 405 (app.rs:466-510).

**Host-owned routes** (plugins may not claim them; overlaps are refused at registration, engine.rs:173-194):

- `GET /api/plugins` — the inventory projection: `{revision ( Desired, the store's current), plugins[], pages[]}`; each row `{id,kind,label,version,enabled,state,configRevision ( Actual, the row version the current instance started with),pages[],lastError?,requires?+requiresMet?}`, absent-not-null (engine.rs:441-489). compiled (the descriptor) is frozen at registration, desired = the store row, actual = configRevision; the drift among the three is exactly the visible gap of "a restart that hasn't happened / an apply that hasn't happened".
- `POST /api/plugins/{id}/enable | /disable` — writes the store row (desired) then reconciles; disable really stops the instance.
- `GET/PUT /api/plugins/{id}/config` — GET returns `{config,schema,revision}`; PUT first runs factory.validate_config (rejected values are not persisted, 400), then CAS-writes (409 conflict), then reconciles; the response is `{revision,config,schema,warnings,applied[,error]}`, where applied:false means the row was persisted but the running instance has not swallowed it (host/api.rs:196-229).
- `GET /api/actions`, `GET|POST /api/runs`, `GET /api/runs/{id}`, `GET /api/runs/{id}/output`, `POST /api/runs/{id}/cancel` — the shared execution plane: POST answers 202 with a runId immediately (the request does not own the background task's lifecycle) and records the caller's `actor` (docs/41 A1; the CLI sends cli:<user>@<host>, the panel sends panel, an omission is recorded as api, services/api.rs:110-176); GET /output streams the live cursor slice a follower polls (services/api.rs:218-258); unknown capability 400, full pool 429 naming the bound (around services/api.rs:93-176).
- `/api/plugins`, together with `/api/actions` and `/api/runs`, is listed on reserved_routes (host/api.rs:31-43): the capability inventory must stay answerable while its providers are stopped.

**Admin API (src/adminapi.rs, mounted inside the main tree)**: GET /api/info (tokenEnv/panelVersion/build); GET/PUT /api/autostart (the one OS-level host setting — start-at-sign-in; no revision to race, the registration IS the store, adminapi.rs:537-557); the full /api/tokens set (CRUD+secret/rotate/delete, the response carrying `groups`+`tokenGroups` since docs/20 G7); the three /api/secrets routes (writes go in, nothing comes out; the GET answers `groups`+`secretGroups` — labels only); /api/traffic (paging + single /{seq} + clear by client); the ONE groups family PUT /api/groups/{scope} + POST …/rename + PUT …/members/{id} + PUT …/order (docs/20, ADR-015) dispatching through the `GroupScopes` registry on AppContext — mcps/tokens register from src/subsystems.rs, conns/rules/jobs/secrets from their owners; whole-list replace where `default` rides in like any name, a group dropped by omission is deleted with its members landing in the FIRST group of the new list, an empty list is the one refusal (400 "at least one group must remain", crates/swiss-host/src/groups.rs), rename keeps its slot and carries both explicit and unassigned members, members store the canonical casing with null meaning no explicit entry; secrets and tokens refuse the order verb (name/creation order IS the order); the retired per-scope routes (PUT /api/order, PUT /api/groups, POST /api/groups/{name}/rename, PUT /api/mcps/{name}/group, the /api/tunnels/groups/* set, PUT /api/tunnels/order) are gone; /api/mcps (GET list/POST create); POST /api/mcpdefs/import (.mcp.json import) and POST /api/mcpdefs/test (a real connection test: DB via ping, http via the initialize handshake, rest a bare GET, all capped at 5s; a rest test passes through the shared resolver first — a missing vault reference fails honestly) — the /api/mcpdefs/* namespace, not /api/mcps/*, because both act on a def payload before any name exists (adminapi.rs:1064-1123, tests nearby); GET /api/memory; POST /api/shutdown (the watch channel is triggered only after the response, adminapi.rs:1274); per-MCP: start/stop/restart (writes managed enabled synchronously), rename (renames the linked tunnels), DELETE (a config-source delete also removes the gateway.config.json entry) + PUT (edit: unmask→build_def→config source stores override, managed source stores directly; a stopped one is not started by an edit), details (config masked), calls/{seq}/tool-history/call/resource (the panel runs them for the browser, which never holds the gateway token), resources-toggle, tools/{tool} (persist first, then swap the live set), {kind} paginated lists (tools|resources|prompts, adminapi.rs:1594-1673); the def-revisions family (docs/28 D1): GET /api/mcps/{name}/revisions (parked snapshots {index,at,note,type}), POST /api/mcps/{name}/replace (parks the current def, installs a new one, note ≤120 chars), DELETE /api/mcps/{name}/revisions/{index}, POST /api/mcps/{name}/revisions/{index}/restore — every fallible step runs before anything is written, and a stopped MCP stays stopped through a def swap (adminapi.rs:1391-1600).

**MCP client endpoints** (docs/24 — the `/mcp/` prefix is the MCP plugin's domain; the root belongs to host chrome and future plugins): POST /mcp/{name} (bearer rejected up front → plugin guard → dispatch via generation-cached handlers; a lazy proc is woken here and only here), DELETE 204, GET falls to 404 (app.rs:351-366,529-533). A POST/DELETE to the old root spelling /{name} of a known MCP answers a dedicated 404 — "moved to /mcp/{name}, update the client URL" (moved_hint_404, app.rs:486-499,593). The JSON-RPC error shape is deliberately not unified with the admin {error} (docs/05 §3, app.rs:181-191).

**Unauthenticated routes**: / (the panel), /admin/*, /health, /health/check (actively triggers a health check over the whole registry) — the loopback guard is their entire boundary; the build stamp deliberately sits on /health (docs/16 H3).

## Panel Pages and Interactions

The panel is the static asset tree embedded in crates/swiss-panel (TypeScript in panel/src with the emit committed, edited directly in this repo, ADR-024); what the host contributes is its **source of data and navigation**:

- **Two-level navigation (docs/13, revised by docs/39)**: level one = the plugin's rail seat, level two = that plugin's pages as underline tabs; grouping is a pure function in page-core.ts, and the data all comes from the pages[] of GET /api/plugins (id/label/order/path/entry/sidebar/layout, descriptor.rs). This build's page table: MCP group Servers (#mcps, 10, sidebar, resource) / Traffic (#traffic, 20) / Token (#tokens, 30); Tunnels group SSH Connections (#tunnels, 30) / Port Forwards (#tunnel-forwards, 35, builtin.rs:297-312); Data (#data, 40, workspace); Jobs (#jobs, 50); Terminal (#terminal, 70, terminal.rs:133-143); Remote group Targets (#remote, 75) / Runs (#remote-runs, 76, src/plugins/remote.rs:123-149). The host-owned trio — Plugins (1000), Secrets (1001), System (1002) — is synthesized by the panel itself, not contributed by a plugin (page-registry.ts:37-41: every plugin may depend on the vault, System controls the one running process). Process has no page: "a capability plugin is reached through the host's /api/actions and /api/runs… a page nobody asked for" (builtin.rs).
- **The entry contract**: what the shell dynamically imports is exactly `/admin/js/views/<id>.js`; renaming an id strands the page (a test pins this, builtin.rs:770-801).
- **The Plugins page** (order 1000, a host asset): renders the state machine plus enable/disable/config editing from inventory; a disabled plugin cannot serve the page that would switch it back, so it must be a host asset (docs/19 §2 makes the same argument).
- **The Secrets page** (order 1001, host-owned like the Plugins page): docs/19's panel presentation; the list gives only names+update time, values are never sent back.
- **Disabled-plugin visibility**: a level-one button of the two-level navigation is marked `· off` when "every page in the group is unavailable" (docs/13 N2); a 503's {error} is shown verbatim by the panel toast.
- **The memory chip**: every panel memory read — the 6 s poll, the chip's click, the r key — goes to /api/memory?tree=1; the server bounds the cost (20 s cache, in-flight dedup, no walk when no proc MCP runs, mem.rs:39,56-87), and a tree-less call gets childrenPending:true. The click re-reads the reading ONLY (`refreshMemoryNow`, polling.js): it never reloads the active view — that was a regression, fixed 2026-09-13 (Node 1cf23dc); the r key keeps the full refresh (`refreshNow` = memory + refreshPage) and stays Data's only manual reload.
- **panelVersion+build from /api/info**: the panel polls the stamp, and when the build changes it **reloads itself** — updates cost no manual refresh (adminapi.rs:385-396).

## Configuration and Storage

**Home directory** (crates/swiss-core/src/paths.rs): `$SWISS_HOME → $SWISS_HOME → ~/.swiss`, the new name first with the old name as fallback; a pre-rename `~/.swiss` keeps serving until `migrate_legacy_home` (called by `swiss start`/`restart` and at `serve` boot) renames it whole to `~/.swiss` — refused while a daemon's pid file in it names a live process; the 19998 test instance points SWISS_HOME at %LOCALAPPDATA%\swiss-test-home (docs/16 H2).

**The full state-file family** (all sealed, all written atomically via tmp+rename, atomic_json.rs):

| File | Contents | Writer |
| --- | --- | --- |
| gateway.config.json | port/host/tokenEnv/servers + root-level subsystem rows + plugins.<id> rows | bootstrap seeding, daemon port writes, adminapi config-source MCP deletes, config_store |
| managed.json | User-added MCPs, overrides, the enabled map, named tokens, sidebar order, groups (the complete ordered list, `default` included, plus a `groupsV2: true` marker riding with any group write; pre-v2 files get `default` materialized at the front on load, and the in-memory list is never empty — a missing/invalid file starts from `[default]`, managed.rs:138-168,619-625) + mcpGroups, since docs/20 G7 tokenGroups + tokenMembers (a sparse id→group map; a revoked id's entry is forgotten), and since docs/28 D1 `revisions` (parked MCP def snapshots, one list per name, capped at five evicting the oldest; a rename carries them along, a remove clears them, managed.rs:368-369,523-562,880-884) | ManagedStore + TokenManager |
| tunnels.json / jobs.json | Per-subsystem state (credentials stored only as ${ENV} references) | The respective subsystems |
| env.json | The sealed .env replacement (overlay) | bootstrap/envstore |
| secrets.json | Secret vault {rev, secrets:{name→value}} (docs/19) | secretstore |
| master.key | The DPAPI-protected master key | Generated by key.rs on first run |
| gateway-<port>.pid / .log, .proc-pids-<port>.json | Instance bookkeeping (plaintext, per port) | pidfile/daemon/proc_pids |

**The v1→v2 projection does not migrate** (config_store.rs:1-2): old root-level rows (jobs/tunnels/mcp…) keep working in place, and versioned `plugins.<id>` rows take **precedence** (an empty one counts too); boot never rewrites the file, only operator changes do. The row grammar is uniform: "turn off jobs" = `{"jobs":{"disabled":true}}` — row addressing and disabling share one grammar (subsystems.rs:5-8).

**The revision mechanism** (config_store.rs:48-56): the top 53 bits of the content sha256 — exactly what fits in a JS number and stays stable across restarts; no metadata is ever stuffed into the file. All write paths use CAS: submit with the old revision, and a mismatch is a Conflict ("configuration changed; reload before saving").

**Credential model (three tiers)**:

1. `${UPPER_SNAKE}` env references — always a reference on disk; expansion happens only at adapter build time (the lenient wrapper at config.rs:76-84; process.exec uses the strict version: a missing variable is a named error, services/process.rs:446-478); the lenient contract is kept: the environment is the machine's current state, and a missing one expands to an empty string (refs.rs:4-6).
2. `secret://kebab-name` vault references — a missing one **hard-fails** naming the reference ("references secret://x which is not in the vault"), refs.rs:7-10; one scanner recognizes both reference families, and a substituted value is never scanned a second time (refs.rs:12-14).
3. Literal values — exist only inside sealed files; replaced by the mask sentinel when the panel echoes them back.

**Schema validation layers**: PUT goes through factory.validate_config (rejected values are not persisted); boot goes through validate_config_for_start (Jobs-specific: bad definitions left by the old validator are drop-and-warn rather than dragging the plugin down, builtin.rs:567-589); config_warnings in the PUT response report "storable but not currently runnable" (e.g. a capability not registered). descriptor.config_schema is schema-lite metadata; the real authority is the v2 definition model (Jobs' full JSON schema is inlined at builtin.rs:455-543).

**chmod discipline**: bootstrap applies chmod_private one by one to the directory and the five sensitive files (bootstrap.rs:138-147); privfs.rs provides the 0600/0700 constants and a Windows no-op.

## Lifecycle and Background Behavior

**Boot order** (src/server.rs:20-263, run_gateway): the environment was already scrubbed at main.rs:13 (the serve path) → PATH repair (login_path_from_env, set_var before any threads) → ensure_first_run → inject_env_store + inject_vault (two lookup paths; vault values never enter the env overlay) → load_config → ConfigStore wraps the raw → port probe **before** orphan reaping (a live instance's ledger is not scanned, server.rs:54-69) → CallLog/Registry/ManagedStore → tunnel objects built first (the start decision has moved into the plugin) → the config MCP registration loop + the managed restore loop (override swaps the def; stopped ones are not resurrected) → the TerminalState seat → RuntimeServices → JobSystem::open (opened unconditionally; the scheduler tick is a plugin decision) → TokenManager (seed = managed's old token ‖ cfg.token) → traffic restore → AppContext → PluginHost: register_all (builtin.rs:91-114: mcp, tunnels, data, jobs, process **registered last so started first** — capability providers before consumers) + the terminal plugin (server.rs:296-300) + the remote plugin (docs/34; registered after terminal with its targets group scope joined to the docs/20 family over the same sealed table, server.rs:301-316) + set_capability_probe (three questions now: connection-catalog / ssh-shell / remote-transport — the last deliberately answered for a plugin that does NOT declare it, so the inventory can say honestly whether remote exec is possible, server.rs:317-337) → start_enabled() (**reverse registration order**: remote→terminal→process→jobs→data→tunnels→mcp; a failed row records failed+lastError and boot continues) → extra routes merged inside the guard and boundary → bind → hourly sweep (calls+run logs).

**Plugin state machine** (descriptor.rs:80-95): Disabled / Idle (reserved for enabled plugins with no eager instance; the P1 built-ins all go straight to Active) / Starting / Active / Stopping / Failed. Note: of the docs/09 §4 draft's EnabledIdle→WaitingDependency→Starting→Active, **WaitingDependency is not implemented** — dependencies surface as the requires+requiresMet data projection rather than a blocking state; the comment at terminal.rs:137-139 still uses waitingDependency design language to explain why it does not declare requires:["ssh-shell"].

**Single-flight and stop order** (engine.rs:266-421): one tokio mutex per plugin serializes lifecycle ops; a concurrent second start queues, re-reads the world, and joins the first result if the slot is already full. start: validate_config_for_start→create→scope.start (START_TIMEOUT 30s; timeout or failure both shut down the scope and record failed). stop: **leave the route slot first** (the entrance closes first; in-flight requests see not-serving) → instance.stop() under STOP_TIMEOUT 10s (on timeout the scope is torn down anyway, lastError recorded) → scope.shutdown() (cancel signal → 5s grace per task → abort). The stop order is "disable must really release": tunnels' stop goes withdraw→drain(3s)→close_all→clear the seat; process's stop revokes both capabilities first, then cancel_action_types awaits in-flight runs; jobs' stop cancels and awaits every run of its own owner (each "what disable really does" comment at builtin.rs:614-746 is docs/09 §4's honesty rule landed).

**The three branches of config change** (engine.rs:285-334): the running instance has first claim on the new row — apply_config applies in place (Jobs: an edit does not bounce the instance or cancel in-flight runs); Failed means the instance stays Active, the revision does not move, and the gap is visible (PUT 200 but applied:false); NotApplicable then depends on restart_on_config_change (tunnels/terminal=true restart; mcp/data/jobs=false only record the revision).

**Process-level background**:
- shutdown triggers: POST /api/shutdown (Windows has no SIGTERM; the watch channel is the signal) or ctrl_c; in-flight requests get 3s to drain (server.rs:306-338).
- teardown order: host.shutdown_all() (reverse registration order: remote→terminal→process→jobs→data→tunnels→mcp; tunnels close before the registry, forwarded ports release while MCP connections drain) → services.shutdown() (unowned runs are collected too) → registry.close_all() → flush calls/traffic (server.rs:340-362).
- daemon: start_daemon does not wait on the child and creates no job object (the child survives the CLI's exit); the loser of a racy double start (dies of EADDRINUSE) cannot falsely report success — only "my own child is still alive" counts as Started (daemon.rs:464-482).
- proc orphans: the kill-on-close job only holds while this process lives; a hard kill (task /End, a crash) leaves orphans, and the next boot tree_kills them via the per-port ledger (proc_pids.rs).
- environment scrubbing: the LAUNCHER_NOISE blacklist (NO_COLOR/CI/TF_BUILD/GITHUB_ACTIONS/CLAUDECODE/CLAUDE_CODE_*/DSH_*/WT_*/TERM_PROGRAM*) is scrubbed once on each of the two paths — start via Command env_remove, serve via in-process remove_var (core/env.rs:78-107; docs/16 H1's 2026-09-11 NO_COLOR incident).

**Logging**: JSON lines {"ts","level","msg","extra"?} println'd to stdout → the daemon redirects them into gateway-<port>.log (core/log.rs:17-28); swiss logs tails by polling (Windows file notifications are unreliable for appends, cli.rs:636-657); 10 MB rotation keeps one generation (daemon.rs:345-353).

## Relationship to the Host and Other Plugins

**The swiss-core ↔ swiss-host division of labor**: core "knows nothing about gateways" (core/lib.rs:1-3) — paths/log/util/atomic_json/env scrubbing/the whole secure family (envelope/key/statefile/envstore/secretstore/refs)/platform (all unsafe FFI is concentrated here, mod.rs:1-4: DPAPI, the Toolhelp32 process tree, KillOnCloseJob, privfs, ConPTY/openpty). host owns the gateway mechanisms: config/config_store/managed/token/auth/local_only/mask/mem/pathenv/reply/proc_pids/dbbrowser (the browser model and the BrowserFlavor vocabulary) + the host engine + the five-piece services set. core depends on no crate; host depends only on core; subsystem crates depend on host; the root src/ is the only crate that sees all ("composition is a file, not a graph", src/lib.rs:1-4).

**One-way dependency between host and plugins**: the host knows nothing about plugins and recognizes only the three traits PluginFactory/PluginInstance/PluginScope (factory.rs); adding a plugin = one factory + one register line, with no match arms in the host (docs/09 §10). The reverse "plugin needs plugin" is expressed as two kinds of data: ① the requires capability name + the host probe's met/unmet verdict (engine.rs:115-151); ② capability seats (catalog/shell) — the provider registers, the consumer leases, and the seat is held by RuntimeServices and so **outlives both plugin instances** (services/mod.rs:49-56). Cross-subsystem type bridging (e.g. tunnels needing to see the registry) lives at the composition layer behind read-only traits (src/mcp_link.rs:1-10).

**Host assets vs plugin assets**: the Plugins page, /api/plugins, /api/actions, /api/runs, /api/tokens (the Token page belongs to the MCP group but the routes are host-owned — "disabling the MCP plugin takes the PAGE off the air but leaves the credential API (and the CLI) serving", builtin.rs:770-775). The MCP client catch-all cannot be a static prefix; client_path_guard asks the host — specifically guaranteeing that "with the plugin disabled, no lazy proc is spawned" (host/api.rs:72-82).

**Concrete relations with the seven subsystem plugins**: mcp = registry + catalog provider; tunnels = shell provider AND remote-transport provider (the RemoteTransportRegistry seat in services/remote.rs) + first-run import moved into start; data = pure consumer (requires:["connection-catalog"]); jobs = one producer on the shared run pool (owner="jobs"; manual runs are "manual", no interference); terminal = the living proof of the public contract (docs/14, zero lines changed under host/); remote = the second public-contract plugin (docs/34: targets/exec/sync/pull over the host's remote transport seam, its builtin MCP under /mcp/remote, deliberately NO requires so the target table stays editable while tunnels is off); process = the capability plugin (registered last of the built-ins, started first). The dbbrowser model lives in host, the drivers in the mcp adapters — Data uses it through leases, with no crate edge.

## Style and Design Observations

**Project-wide patterns this layer follows and demonstrates**:

- **Plugin descriptor registration**: adding a capability = a data declaration (descriptor/pages/routes/requires) + one register line; id and route-prefix conflicts are loudly refused at registration (engine.rs:159-211), and a silent shadow route is treated as a boundary hole.
- **Route mounting**: "paths are stable, dispatch looks at live state" — routes stay mounted forever, with one cheap question per request (is_active); disabled = the instance is really Dropped, not an enabled bool. All plugin trees sit inside the loopback guard, and the extra tree gets its layer attached separately (an axum layer covers only routes that exist at mount time — the lesson of app.rs:446-451).
- **Error handling**: every failure is a value, not a panic — ActionOutcome/ApplyOutcome/ConfigStoreError/string errors carry the Node build's original text; a failing MCP/plugin/task is isolated as one log line; no unwrap on config/network/db/fs; a panicked plugin task is simply reaped (scope.rs:112-122), and a panicked action is just one Failed run (runs.rs:1080-1102).
- **Naming**: wire shapes are camelCase + absent-not-null (JSON.stringify semantics faithfully ported); `lmg`/`lmg-state-v1`/`node-original/v1` are frozen historical literals whose names are never touched (envelope.rs:29-31;key.rs:31); the paired pattern of new-name SWISS_* first with old-name SWISS_* as fallback runs throughout (HOME/PORT/TOKEN/MASTER_KEY).
- **UI presentation**: the panel JS is the spec for the admin API (ADR-009); the Rust side only guarantees field-by-field shape equality; the mask sentinel round trip guarantees the browser never obtains credentials; the vault's values-in-nothing-out is a deliberate one-way door.
- **Memory discipline**: bounded capture truncates while reading; read pipes join without hanging; runs are bounded and rejection is visible; child processes start lazily; every MB number is honest (childrenPending rather than a confident 0); two supervisor comments record "the old runner's unbounded read_to_end" directly as a cautionary tale (process.rs:8-15).
- **Cancellation semantics**: a watch channel rather than abort (CancelSource uses send_replace so a refused send cannot lose the cancel, action.rs:87-95); cancellation awaits until the child process is reaped; the stop order "withdraw the entrance first → grace → forced teardown" has the same shape in five places — scope/runs/catalog/shell/daemon (withdraw→drain→close).
- **Adoption and migration**: plaintext config is re-sealed on first read, .env is deleted only after verification, and the old validator's definitions are drop-and-warn — every migration is "clean after one boot", and on failure the original state is kept.

**Inconsistencies/exceptions (found in this audit)**:

1. **The WaitingDependency state is not implemented**: the state machine at docs/09:115 has it, the enum at descriptor.rs:80-95 does not (Idle is the reserved slot); dependencies instead use the requires/requiresMet data projection. The comment at terminal.rs:137-139 still cites this unimplemented state as a design reason — doc language running ahead of the code.
2. **The mem.rs module comment is stale**: two places near the top say "/api/mem" and "/api/mem?tree=1" (mem.rs:18,52), while the actual route is /api/memory (adminapi.rs:1035, and daemon.rs:611 likewise) — a Node-era leftover sentence.
3. **The plugins/mod.rs comment points at src/host** ("The host and the built-ins live in src/host", plugins/mod.rs:3); after the P5 workspace split they actually live in crates/swiss-host/src/host and src/builtin.rs — the path was never updated for the split.
4. **/api/mcps/{id}/secret is a plaintext exception to the "shown only once" principle**: the token secret can be read back at any time (the comment at adminapi.rs:428-433 defends itself: verify compares in plaintext anyway, cat can get it too, and a loopback caller reading it buys no secrecy) — a deliberate asymmetry against the vault's values-in-nothing-out (the two credential classes have different threat models).
5. **process.exec's env references are strict while legacy-command's are lenient** (the x-env-refs declarations at actions.rs:193,269 respectively) — a deliberate era divide rather than an inconsistency, but two contracts coexisting on one layer is worth knowing.
6. **The CLI's open uses `cmd /c start`** (cli.rs:687-694): the project rule "no subprocess where a syscall exists" here gives way to "use the platform's default opener", and CREATE_NO_WINDOW contains the cost — a recorded tradeoff, not a violation.
7. **The 6b84f26 groups rework left stale comment fragments**: the DEFAULT_GROUP doc comment still opens with the retired sentence ("The group every MCP belongs to until it is put somewhere else. Deliberately NOT stored: an", managed.rs:26) directly above its replacement; the /api/groups and /api/mcps/{name}/group route comments still say members "return to the default group" (adminapi.rs:643-645,711-712); and the /api/mcps row comment still promises "an unassigned MCP answers \"default\"" (adminapi.rs:769) — the sink is now the FIRST group slot, whatever its name.
