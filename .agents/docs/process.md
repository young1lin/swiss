# Process Capabilities and Shared Process Supervision (swiss-host / swiss-core::platform)

> The process plugin + the execution foundation shared by the whole process: the two capability actions process.exec / process.legacy-command spawn/watch/reap subprocesses through the shared Supervisor; the RunCoordinator gives every background execution a bounded, owner-accounted, first-wins-terminal-state run registry; the proc MCP subprocess's lazy wake, idle reaping, PID accounting and orphan settlement, plus process-tree memory metering, all land on this chain; the platform layer replaces every powershell subprocess with direct Win32 calls.

## HTTP API and Routes

- Host-owned, resident and never withdrawn: GET /api/actions; GET+POST /api/runs; GET /api/runs/{id}; GET /api/runs/{id}/output; POST /api/runs/{id}/cancel (crates/swiss-host/src/services/api.rs:59-67, ROUTES constant :46). The capability list rises and falls with providers starting and stopping, but the routes themselves are always there — a stopped provider's historical runs remain readable (api.rs:1-14 module comment).
- Mounting: src/server.rs:263 merges swiss_host::services::api::mount into the extra tree, inside the loopback guard and plugin boundary together with terminal/tunnels/jobs; the process plugin itself has routes: [] — it is reached through the host's generic surface; this is the difference between a "capability plugin" and a "page plugin" (src/builtin.rs:677-684).
- Submission semantics: action required; timeoutMs defaults to 600_000 (10 minutes, matching the docs' job default), capped at 24 h; queueIfBusy defaults to false — a full pool answers 429 naming the capacity, not an invisible queue (api.rs:36-41, 113-131); unknown capability 400, capacity full 429 (api.rs:144-145).
- Response shape: RunView's to_json is camelCase + absent-not-null (runs.rs:322-398): runId/owner/label/actor/action/state/queuedAt/startedAt/endedAt/ms/pid/exitCode/timedOut/canceled/error/chars/outputTruncated/meta/output — timestamps are RFC3339 strings, output rides only the single-run GET (`?output=0` drops it), actor is the audit trail's who column (docs/41 A1: `cli:<user>@<host>`, `mcp:<token label>`, `panel`, `jobs`, or `api` for an unnamed /api/runs caller), and meta carries the action's own extras (a remote run's target and endpoint); the panel JS is the spec — the wire type it reads is ApiRunRow in panel/src/types/api.d.ts (AGENTS.md).

## Panel Pages and Interactions

- Memory chip (global chrome): crates/swiss-panel/src/admin_assets/js/polling.js:26-45 — every panel memory read (the 6 s poll, the chip's click, the r key) goes to /api/memory?tree=1, so childrenMb shows whenever the walk succeeds; a childrenPending: true result hides children and asks for a click to retry. The click re-reads that reading ONLY — the active view is never reloaded (`refreshMemoryNow`; the old click-also-reloaded behavior was a regression, fixed 2026-09-13, Node 1cf23dc); the r key keeps the full refresh (`refreshNow` = memory + the current view). The tooltip gives gatewayMb, proc-MCP children Mb across N processes, and the retryable hint for childrenPending.
- MCPs page: rows with an idle lifecycle are dimmed (js/menu.js:79, text idle — lazy: no child yet, wakes on the first request); the edit form's autostart toggle writes the lazy field, with a hint saying "off by default: the child is only started by the first client request, and reaped after 10 idle minutes (idleMs adjustable)" (js/fields.js:13-22) — the proc subprocess is the only truly memory-consuming resident thing in the whole process, and the UI puts that fact next to the form.
- Jobs page: Run now submits async then polls /api/runs/{id}; closing the page does not cancel the job; the terminal-state toast reports succeeded/failed + duration (js/jobs.js:133-162); the job definition form's action input is built dynamically from GET /api/actions's schema + read back by the JSON editor (js/jobs.js:475); run-history (runlog) rows show state/duration/output tail.
- The Process plugin has no page or nav tile of its own (builtin.rs:677-684 comment: a tab for it would be a page nobody asked for) — its entire visibility is the toggle row on the Plugins page and the indirect appearances above.

## Configuration and Storage

- Plugin config: the process plugin's config_schema is an empty object, restart_on_config_change: false (builtin.rs:676-682); the real knobs live on the consumer side — the jobs plugin's maxConcurrentRuns/maxQueuedRuns reset the shared pool via set_capacity (runs.rs:269-277; defaults DEFAULT_MAX_CONCURRENT_RUNS = 2, DEFAULT_MAX_QUEUED_RUNS = 32, runs.rs:45-46).
- Action input: process.exec accepts program (required, non-empty), args (a string array, one argument per element), cwd, env (an object whose values may carry ${ENV_VAR} references); unknown keys 400 (actions.rs:82-135). Reference expansion happens only at the action layer, strict style naming the missing variable (process.rs:442-478); the old lenient expansion keeps Node semantics (unset → empty string).
- Run output budget: a 16 KiB tail per pipe (DEFAULT_OUTPUT_MAX_BYTES, process.rs:51); ProcLimits default deadline 10 minutes (process.rs:163-170); history ring FINISHED_RING = 32 entries, each storing only capped output (runs.rs:39-41).
- proc PID ledger: <data dir>/.proc-pids-<port>.json (proc_pid_file, proc_pids.rs:40-42) — port-scoped: when two instances coexist on different ports, instance B's settlement will not kill instance A's live subprocesses (proc_pids.rs:18-20); writes go through temp+rename atomic replacement (proc_pids.rs:76-81) so being killed mid-way cannot corrupt the read; a successful build records (proc.rs:701 note_proc_pid), a clean close un-records (proc.rs:525 drop_proc_pid), and at startup it settles first then kills (proc_pids.rs:139-172).
- Memory metering cache: subtree walk results are cached for 20 s (CACHE_MS, mem.rs:38-39); invalidate_memory_cache expires them immediately after start/stop/restart (mem.rs:42-46).
- proc timeout knobs: PROC_HANDSHAKE_TIMEOUT_MS (default 60 s, enough for npx/uvx cold starts), PROC_CALL_TIMEOUT_MS (default 180 s, for large screenshot/inference calls exceeding the SDK's 60 s default), and a per-MCP timeoutMs (proc.rs:50-68).

## Lifecycle and Background Behavior

Subprocess lifecycle (spawn → kill → reap, all inside Supervisor::run, process.rs:235-395):

- spawn: tokio Command, stdin null, stdout/stderr piped, kill_on_drop(true); on Windows add CREATE_NO_WINDOW (0x08000000) — a console-less daemon must not flash a console for every subprocess (process.rs:267-272); on Unix start a private process group process_group(0) so a later kill(-pgid) reaches any depth, the equivalent of the Windows job object (process.rs:273-280).
- Windows subtree armor: child.raw_handle() is attached into a kill-on-close job object at spawn time via KillOnCloseJob::assign — one handle owns the whole tree, naturally PID-reuse-safe; hard-killing this process makes the OS close the handle and slaughter the tree (process.rs:293-297; crates/swiss-core/src/platform/job.rs:52-78). This is ADR-008's single mechanism; the proc adapter, the jobs runner, and the local terminal all attach through the same function.
- Accounting by PID: PidGuard registers live root PIDs into Supervisor.pids and un-registers on Drop — even a panic leaves no stale registration (process.rs:194-207, 286-291); the memory view and the orphan settlement each take their root set from here/the registry.
- The three-branch endgame uses select with bias, cancel first: when cancellation and natural exit coexist on the same tick, cancellation is the outcome the caller wants (first-wins starts here) (process.rs:313-329); timeout/cancel/wait failure → kill_tree: on Windows drop(job) first so the handle closes (this is the tree slaughter), then top up with the root's start_kill + reap within the 3 s KILL_WAIT; on Unix kill(-pgid) + start_kill + wait within the limit, leaving no zombies (process.rs:331-344, 412-429).
- Pipe readers: two read_bounded tasks read into BoundedCapture's fixed tail buffer as they go — "capped at read time"; a chatty subprocess can never first bloat the process and then be trimmed (process.rs:53-97, 100-129; module comment :9-12); after the process dies the readers only wait for the pipe to close; if it stays open too long (descendants holding inherited handles) they abort after 5 s (DRAIN_GRACE); bytes already read are all kept; tasks are joined or abort+reaped, never detached (process.rs:398-410).
- Output assembly: stdout + stderr tagged with [stderr]; on Windows, decoded by code page (GBK) so Chinese characters do not garble (decode_child_output — historically homed in proc.rs, now living in process.rs, proc.rs:70-72); resolved reference values (≥8 chars) are all masked into the panel's own mask style, so a subprocess echoing its own credentials cannot write them into run history (process.rs:360-372, 431-440; actions.rs:62-78).

Run registry (RunCoordinator, runs.rs):

- Three invariants (module comment :1-24): BOUNDED (both concurrency and queue have caps; exceeding them is a visible capacity error), OWNER-SCOPED (owner accounting: stopping Jobs cancels only jobs' runs, manual ones continue; no ownerless detached tasks), FIRST-WINS (in the deadline/cancel/exit race only one can write the terminal state; a late cancel is an idempotent no-op reporting the terminal-state view).
- Submission: submit validates capacity → immediately returns SubmittedRun{run_id, done oneshot} (runs.rs:291-340); queue_if_busy decides whether to keep one successor or reject; the dispatch loop starts drive_action one by one.
- Deadline and cancel: a deadline does not drop the task but goes through cancellation — the action stops cleanly via CancelSource and reports honestly, the result marked timed-out; the coordinator accepts only actions whose cancelable() is true (a non-stoppable capability would squat a slot forever — exactly the wedged-forever case the deadline exists to prevent); cancel awaits the run task — by return the subprocess is reaped and the readers joined; dropping a JoinHandle and pretending not to see does not count as cancellation here (runs.rs:16-24, 503-541).
- panic isolation: an action's panic is caught by catch_unwind into a Failed run (the error text includes panicked), the slot is released as usual, the pool is not poisoned (runs.rs:1080-1102 tests).
- The scope-cancellation trio: cancel_owner (jobs/manual), cancel_action_types (used when disabling process), shutdown_all (the gateway's own wind-down, RuntimeServices::shutdown → runs.shutdown_all, cleaning up all in-flight runs before process exit) (runs.rs:546-564; services/mod.rs:71-75).
- The label overlap gate: count_for_label gives the jobs scheduler its overlap decision (a same-named job already running means no duplicate start) (runs.rs:279-286).

Accounting and idle reaping of proc MCP subprocesses:

- Laziness: is_lazy — the proc type defaults to lazy, other types default to start-at-boot with an explicit lazy: true opt-in (the panel's autostart checkbox writes the same field) (registry.rs:81-92); Idle is a first-class Lifecycle state (startable on demand ≠ stopped).
- Wake: the first request on the MCP routes goes through ensure_started, Idle → Starting → Started; waking immediately arms arm_idle (registry.rs:275-293, 373); every served call's note_traffic pushes the deadline back (registry.rs:294-307); idleMs: 0 exits reaping entirely (registry.rs:309-331).
- Reaping: start_timer starts two background tasks — a health-probe interval loop + an idle sweep once per second (concentrating the Node version's per-entry setTimeout into one sweeper); on expiry do_stop runs: stop the subprocess, lifecycle back to Idle (wakeable again), the log mcp idle — reaping child naming name and idleMs (registry.rs:586-611, 644-674).
- Orphan settlement: boot order = set_proc_pid_file (the configured port names the file) → reap_proc_pids(own_pid) before any proc MCP starts (src/server.rs:53-68); the ledger is cleared and re-recorded; each live non-this-instance descendant PID is tree_kill-ed one by one; on a descendant_pids snapshot failure it fail-closes and skips this round (orphans are left for next time — far better than wrongly killing a subprocess this instance just started) (proc_pids.rs:139-172).

## Relationship to the Host and Other Plugins

- RuntimeServices is this layer's home: the five-piece set of actions (ActionRegistry) + runs (RunCoordinator) + supervisor (Supervisor) + catalog + shells, constructed outside the plugins and outliving plugin instances (crates/swiss-host/src/services/mod.rs:42-69); the process plugin, Jobs, the manual API, remote (docs/34), and proc MCP are producers/consumers on the same pool.
- Registration order is startup order: ProcessPlugin registers last in register_all (src/builtin.rs:81-86) — boot walks in reverse, so it starts first; a capability provider must be online before any plugin that might submit runs to it.
- start half-registration self-healing: if the second action fails to register, the first is rolled back before erroring — no plugin that "reports active but is missing half its capabilities" exists (builtin.rs:709-725); stop unregisters first, then cancel_action_types — withdrawing resolution eligibility before reaping in-flight runs, so new submissions get 400 rather than silently doing nothing (builtin.rs:727-745). The consequences of disabling are honest: the Jobs scheduler keeps running, and its process-type jobs report "capability unavailable" — exactly the dependency-unavailable outcome docs/09 §9 wants (builtin.rs:694-702).
- Jobs is a producer: submissions under JOBS_OWNER (jobs) via services.runs.submit (crates/swiss-jobs/src/jobs/mod.rs:596, 722); manual runs use owner manual (api.rs:50); stopping Jobs does not touch anyone else's runs (runs.rs:546-549).
- Remote is on the same pool from the capability side (docs/34): its remote.exec/sync/pull/cat/write actions register into the ActionRegistry (register_all, crates/swiss-remote/src/actions.rs:1092-1102), the CLI (`swiss remote …`) and the remote MCP tools submit them through POST /api/runs, and the plugin donates the coordinator's durable run record — the RunHistorySink seat (runs.rs:79-100; crates/swiss-remote/src/history.rs, added at plugin start via add_history_sink) whose 30-day/500 MB log the Remote Runs page reads.
- Division between actions and the supervisor: the action layer only handles input semantics (parsing/validation/mask collection); the lifecycle is delegated entirely to the Supervisor; COORDINATED_TIMEOUT_MS = u64::MAX — actions set no deadline of their own, and the run coordinator is the sole deadline owner (cancellation via CancelHandle; tree-kill and reader joins all happen inside the supervisor's cancellation path) (actions.rs:28-32).
- The proc adapter does not go through the RunCoordinator: a resident MCP subprocess is not "one run" (process.rs:5-6 module comment); it has its own lifecycle (registry) but reuses the same platform teardown mechanisms (job object, tree_kill) and the same PID ledger — lifecycles separate, platform mechanics unified, which is precisely why this layer exists.
- The platform layer is the only unsafe zone: KillOnCloseJob's FFI, Toolhelp32 snapshots, GetProcessMemoryInfo, and DPAPI all live in swiss-core/src/platform; swiss-host is therefore zero-unsafe (process.rs:16-22); the process-tree BFS (walk_descendants, incl. cycle protection and the "exclude own pid" semantics) is shared by memory metering and orphan settlement (platform/mod.rs:37-67).
- Panel assets live in this repo since ADR-024 — authored in crates/swiss-panel/panel/src/*.ts with the emit committed under src/admin_assets/js (docs/36); the memory JSON shape (MemoryInfo's camelCase fields, childrenPending semantics) stays field-for-field Node-shaped; the heap fields are honestly filled with private-commit on the Rust side, with externalMb pinned to 0 (mem.rs:1-12).

## Style and Design Observations

- Plugin descriptor registration: process is the exemplar of a "pageless capability plugin" — the descriptor declares pages: [], routes: []; the host faces it through the generic /api/actions and /api/runs; a new capability touches no host match arm (builtin.rs:677-684; docs/09 §3).
- Shared mechanism, not shared business: the supervisor/run pool/registries are a textbook case of "the host keeps only cross-cutting mechanism" — Jobs, manual, and future plugins are all producers, and the host favors none; the two consumers (proc resident subprocesses vs jobs one-shot commands) deliberately have separate lifecycles and deliberately share platform mechanics (process.rs:1-22).
- Error handling: rejections are visible and typed — unknown capability 400, capacity full 429 naming the cap, missing env var naming the variable, half-registration self-healing; a panic is a Failed run, not a process crash; unwrap appears only in the lock unwrap_or_else(into_inner) recovery idiom — no bare unwrap on config/network/filesystem paths.
- Memory discipline: this is the densest layer of the project's founding principle — capping at read time (not accumulate-then-trim), readers joined not detached, a 32-entry history ring, proc subprocesses lazy + idle reaping (the product's single biggest memory feature), skipping even the descendant walk when the PID ledger is empty (proc_pids.rs:143-145), memory metering with a 20 s cache + lazy tree parameter.
- The no-powershell discipline: the Node version spawns a powershell with a ~65 MB transient working set for every process-tree walk; here it is all direct Win32 calls, which is why the memory view went from optional to default (windows.rs:1-3). A new Command::new("powershell") needs a very good excuse in this repo (AGENTS.md).
- Terminal-state uniqueness: biased select + first-wins + idempotent cancel is the consistent vocabulary running through runs and the supervisor; cancellation always waits for completion (reap+join) rather than firing a signal and leaving.
- Naming and wording: ProcResult's ok means exactly "exit 0 within the deadline and not canceled"; every other path carries its own flag (timed_out/canceled/error/output_truncated); logs name names (name, pid, idleMs, runs counts) so bug reports can tell them apart.
- Platform boundary: unsafe is only allowed to live in swiss-core/src/platform (platform/mod.rs:3-4); swiss-host and the subsystem crates are therefore zero-unsafe, and the FFI SAFETY comments state handle ownership and lifetimes item by item.

Inconsistent exceptions (all deliberate and on record):

- process.legacy-command's lenient references coexist with process.exec's strict references — two strictness levels in one registry, to keep the Node-era jobs.json semantics (unset variable → empty string) from silently changing meaning; the docs say plainly this is a compatibility shape, not a model for new code (actions.rs:9-16).
- proc MCP subprocesses do not enter the RunCoordinator (a resident subprocess is not a run) yet still reuse the supervisor's platform mechanics and PID ledger — layering is cut by "lifecycle shape", not by "whether subprocesses are involved".
- The process plugin registers last in register_all to gain first startup — the ordering semantics (reverse startup) are an implicit contract, maintained by comments and tests, not enforced by the type system.
- The memory JSON's heapUsedMb/heapTotalMb are filled with private-commit on the Rust side (there is no V8 to ask), and externalMb is always 0 — the shape is faithful to Node, the values are honestly labeled; mem.rs:8-12 records this "honest approximation" in the module header.
